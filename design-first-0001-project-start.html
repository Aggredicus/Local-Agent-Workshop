01 · Decision surface

Executive summary

The design-first workflow should make the next coding step obvious before implementation begins.

Recommended decision

Begin with a CLI-and-Markdown-first MVP centered on the canonical instruction spine (`me.md`), branch policy enforcement, Chronicle events, review cards, and a minimal `workshop init` command before building the dashboard or escalation integrations.

Why this design

This preserves the core governance model early while avoiding premature UI complexity. It creates the minimum useful loop: initialize a governed repo, choose a small task, work on an isolated branch, verify, generate a review card, and resume safely.

03 · Problem framing

Problem frame

Define the real user need before choosing an implementation path.

User / operator

Primary operator is Dillon: an advanced AI-assisted builder who wants local-first control, low-cost automation, overnight grind loops, clear morning review surfaces, and eventual Signal/Telegram escalation only for critical decisions.

Job to be done

When starting or improving a repository, the operator needs an agent-governed workspace that can prepare high-quality work autonomously while preserving branch safety, traceability, and human decision authority.

Success outcome

A user can import the repo, run a small set of commands, create protected branches, launch a safe task, receive a review card, approve or modify the work, and resume the next task without losing context.

Non-goals

  • Do not build a full SaaS platform in the MVP.
  • Do not start with a large multi-agent swarm.
  • Do not allow silent production changes or protected-branch merges.
  • Do not implement live Signal/Telegram escalation before the local review loop works.
  • Do not optimize for a polished dashboard before the underlying artifacts are stable.

04 · Constraints

Constraints and invariants

Identify what the design must preserve even if implementation details change.

Functional constraints

  • Every agent/tool adapter must point to `me.md` as the instruction spine.
  • The MVP must produce durable artifacts: Chronicle events, review cards, reports, and branch-aware state.
  • The system must support long-running work through checkpoints and resumability.
  • The system must provide clear next actions: approve, reject, modify, pause, resume, promote, or release.

Governance constraints

  • Protected branches require explicit human approval before merge.
  • Sensitive work may be drafted, tested, simulated, and reviewed, but live consequences require approval.
  • Agents must create reviewable patches instead of silently mutating stable branches.
  • The workshop may improve its own skills and workflows only through reviewable proposals.

Technical constraints

  • Start with a Python CLI named `workshop`.
  • Use Markdown, JSON, and HTML artifacts before a dynamic web dashboard.
  • Use `.branch-policy.yaml` as machine-readable branch governance.
  • Use schemas for events, run state, review cards, risk assessments, and design-first reports.
  • Keep remote APIs optional and local-first operation preferred.

Environmental / budget constraints

  • Prefer local model and local script execution where practical.
  • Avoid repeated failure loops and wasteful full-suite test runs.
  • Use cheap checks on `agent/*` and `experimental`; reserve full checks for `develop`, `release/*`, and `main`.
  • Track future wall time, model usage, remote calls, repeated errors, and estimated energy footprint.

05 · Architecture comparison

Architecture options considered

Compare viable options before selecting a design.

Option A

Artifact-first CLI MVP: build `workshop` as a local command that reads policy files, writes Chronicle events, creates review cards, and generates Markdown/HTML reports.

Tradeoff: Fastest safe path and easiest to test, but less visually impressive until the dashboard arrives.

Option B

Dashboard-first MVP: build the morning review cockpit immediately and wire backend behavior into it later.

Tradeoff: More motivating UX, but risks hiding weak governance behind a polished interface.

Option C

Agent-runner-first MVP: focus first on autonomous branch/worktree execution and long-running grind loops.

Tradeoff: Gets to automation quickly, but risks unsafe behavior before branch policy, review cards, and event schemas are stable.

06 · Chosen path

Chosen design

The recommended architecture slice to implement next.

Design proposal

Choose Option A first: an artifact-first CLI MVP. Implement the smallest reliable governance loop before agent autonomy becomes powerful. Then layer sandbox runner, repo graph, resumable grind, dashboard UX, and escalation bridge on top.

07 · Risk and approval

Risk boundaries

Surface sensitive consequences before implementation begins.

Low risk allowed

  • Docs, schemas, placeholder tests, report templates, and example artifacts.
  • Local-only CLI scaffolding with no external side effects.
  • Review card and Chronicle event generation using sample data.
  • Non-destructive repo graph placeholder generation.

Review required

  • Branch policy enforcement behavior.
  • Sandbox/worktree creation and cleanup.
  • Risk classifier defaults.
  • Any dependency additions.
  • Any automation that creates commits or branches.

Human approval required

  • Protected branch merge.
  • Production deployment behavior.
  • Live credential use or secret rotation.
  • Payment/auth live-effect behavior.
  • Destructive file, Git, or remote repository operations.
  • Signal/Telegram notification behavior that could expose sensitive context.

10 · Human decision

Approval gates

Clarify whether implementation can proceed automatically or needs human input.

Proceed condition

Proceed with implementation once the starter repository is imported, `main`, `develop`, and `experimental` exist, branch protections are configured, and the first small PR confirms CI is running.

Stop condition

Stop or request human approval if implementation would require live credentials, protected branch merges, destructive Git cleanup, production deployment, payment/auth live effects, or notification of sensitive content through an escalation channel.
