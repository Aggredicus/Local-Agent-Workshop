# Windows USB ISO path fix

Qualified implementation: ed92308, based on reviewed main 902d36d. User screenshots showed quoted drive strings parsed as a drive named "C, an existing ISO refused by option 2, and a containing folder rejected by option 3. The program also defaulted to Desktop after a download into a different folder and treated every reparse point as a link. This was software usability/validation friction, not a Ventoy-formatting failure.

Changed: normalize balanced File Explorer quotes, accept ISO files or containing folders, offer an optional native file picker, remember the current session's verified download location, verify/reuse existing downloads, distinguish concrete lookup/checksum/link/hash errors, and classify OneDrive data placeholders separately from actual symbolic links/junctions. Executable payload/startup link checks remain strict. The published law-iso-d2ab3794cf9f SHA256 is bundled as a fallback when that image's separate sidecar was not downloaded; any other unmatched content is rejected. The USB checksum is created from the digest actually verified, using CreateNew, and the USB ISO is checked again. No existing files are overwritten; existing LAW/ISO destination guards and COPY confirmation remain.

Verification: 215 Python tests, repository contracts/schemas and Ruff passed. Native Windows PowerShell 5.1 CI passed (https://github.com/Aggredicus/Local-Agent-Workshop/actions/runs/43781746935), including the real option-3 copy on an isolated NTFS folder mapped with subst, quoted Documents folder selection, all payload/ISO/checksum copies, existing-file preservation and menu return. Unit/integration checks cover quoted file/folder forms, existing-ISO reuse with no network request, remembered defaults, cloud-placeholder metadata classification, missing sidecars, invalid names and tampering. Source tests and the Windows job also passed in the branch USB workflow (43781747023).

The actual published 1,091,436,544-byte ISO was separately verified with the production fallback constant and no sidecar: 360b0048d297d425dd7bc4c4e801c7f9aa1f5e6dc804b3ba7948c0e640ec7844. The private test used a hard link to the existing public download; no 1 GB redownload was required. The native picker and live OneDrive hydration were not UI-tested here; classification uses synthetic metadata, and the full real filesystem test covers the user's quoted-folder flow. No physical USB, Wi-Fi or credential operation ran.
