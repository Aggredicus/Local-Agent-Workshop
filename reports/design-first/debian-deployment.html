Debian deployment: design before implementation

Run: debian-deployment · Risk: high · Decision: proceed with implementation and disposable tests; no production activation.

Operator need

ThinkCentre1 runs a ZIP-compatible Windows launcher. ThinkCentre2 retains its existing Debian installation. Additional machines have explicit user-chosen identifiers.

Options

A new Ansible/web framework adds Python dependencies and remote privileged automation. Chosen: extend the existing Python standard-library workshop CLI, OpenSSH transport, static local browser interface, and bounded Linux helpers. This reuses CLI contracts and makes the source ZIP useful offline when Python/OpenSSH are already installed.

Invariants

No implicit host trust, network scanning, arbitrary remote shell input, Docker socket sharing, Docker group membership, destructive disk operation, manager replacement, or automatic deployments. Read-only browser; privileged changes require a terminal approval bound to the reviewed plan. Rootless Docker is the supported initial runtime; rootful migration is blocked. Administrative ports bind loopback. LAN access uses an SSH tunnel until a Docker-aware firewall is validated in VMs.

Slices

  1. Windows launcher and local authenticated setup UI
  2. Validated SSH profiles and safe read-only inspection
  3. Local Debian bootstrap, credential-safe Wi-Fi and rollback
  4. Official signed Docker packages and rootless startup
  5. Declarative restricted project deployment, health/rollback/history and backup verification
  6. Offline signed-APT bundle builder and integrity verification
  7. Tests, operator guides and security review

Risk gates

Only disposable testing is authorized here. Host changes, SSH pairing, installation, application deployment, and recovery on physical servers need the operator's explicit approval. Network/firewall automation stays unavailable unless its backend-specific isolation and reconnect tests can be demonstrated. No public publication or protected-branch mutation.
