01

Prepare without losing Windows

Disk warning. Installing Debian onto a Windows drive may erase Windows 11, applications, BitLocker recovery partitions and personal files. Do not pick "use entire disk" without confirming backups and the intended target. If preserving Windows matters, use a separate SSD or a carefully planned dual boot.

Download the signed Debian 13 amd64 netinst image from Debian's official download page; verify the checksum/signature using Debian's instructions. Write the image to a spare USB drive with a trusted USB-image writer. The USB drive will be overwritten.

A direct Debian installation is our target. If you prefer a no-reformat trial, run Debian as a virtual machine first; do not mistake WSL2 for native Debian server installation.

02

Install Debian 13 on ThinkCentre A and B

Use Debian's installer to select SSH server and standard system utilities. Skip the desktop environment if these will be dedicated servers. If installation does not include OpenSSH, on each Debian machine run:

sudo apt update
sudo apt install -y openssh-server python3 sudo
sudo systemctl enable --now ssh
cat /etc/debian_version
hostname

If the user you created cannot use sudo, use Debian's local root console to add the account to the sudo group according to your installer choices; log out and back in before retesting.

04

Prepare the Ansible controller on A

git clone -b agent/debian-server-deployment https://github.com/Aggredicus/Local-Agent-Workshop.git
cd Local-Agent-Workshop/infrastructure/debian
bash scripts/bootstrap-controller.sh
cp inventory.ini.example inventory.ini
nano inventory.ini
ansible-galaxy collection install -r requirements.yml

Controller location: ThinkCentre A can manage both A and B through normal SSH, including connecting back to itself using its LAN address. Ansible does not require an agent service on B.

05

Provision both Docker hosts

Only proceed after SSH and sudo work on both nodes. These commands run from the infrastructure/debian directory on A.

ansible -i inventory.ini law_nodes -m ping --private-key ~/.ssh/id_ed25519_law
ansible-playbook -i inventory.ini preflight.yml --private-key ~/.ssh/id_ed25519_law --forks 2
ansible-playbook -i inventory.ini site.yml --private-key ~/.ssh/id_ed25519_law --forks 2 --ask-become-pass
What gets installed: Docker Engine and Compose from Docker's signed Debian APT repository, plus an intentionally limited BusyBox test container. The test HTTP port binds only to 127.0.0.1:8088 on each server; it is not an AI server and cannot execute agent commands.

Different sudo passwords? Use encrypted per-host Ansible Vault credentials rather than sharing a single interactive become password. Never place cleartext credentials in the public repository.

06

Verify each server independently

ansible-playbook -i inventory.ini verify.yml --private-key ~/.ssh/id_ed25519_law --forks 2 --ask-become-pass
# On EACH server, separately:
sudo docker ps
curl -fsS http://127.0.0.1:8088/

Expected output includes LAW Docker host: healthy. Note that the container is deliberately inaccessible from other LAN computers through port 8088.

Rollback the verification container

sudo docker compose -f /opt/law/compose.yaml down

That stops the test service, but does not uninstall Docker or restore Windows. A full disk-image restoration is the separate fallback for operating-system installation.

07

Rust swarm: preserve, review, then opt in

The draft Rust swarm PR #193 already contains a bounded, SSH-based two-node worker. It has durable event journaling and only three side-effect-free operations: uppercase, word count and integer sum. It does not provide an AI model, automated agent scheduling or general-purpose command execution.

ansible-playbook -i inventory.ini rust-swarm.yml --private-key ~/.ssh/id_ed25519_law --forks 2 --ask-become-pass -e rust_prototype_review_approved=true

This optional command is not part of the default deployment; it must not be used as a shortcut around PR review. Its worker uses verified SSH host keys and a fixed remote executable, not a public API listener.

08

Future GitHub-triggered deployments

Public repository caution. Do not attach a privileged self-hosted runner directly to this public LAW repository. A malicious public pull-request workflow can compromise an exposed local runner. GitHub's own security guidance strongly discourages that pattern.

Use the checked-in github-actions/PRIVATE_DEPLOY_TEMPLATE.yml in a new, restricted private deployment repository. Install its runner on ThinkCentre A with a dedicated unprivileged account and verified SSH credentials. Store the real inventory privately, and use encrypted Ansible Vault credentials for unattended sudo.

The private workflow deploys an immutable, reviewed LAW commit SHA, manually triggered from GitHub's Actions page. A private environment approval gate can be added where your GitHub plan supports it.

Troubleshooting

SSH refuses connection

Confirm Ethernet/IP, OpenSSH installation, firewalls, the actual username and port 22 accessibility from the controller. Use the local console rather than disabling host-key verification.

Ansible prompts for a password or fails sudo

Check authorized SSH keys, specify the correct key with --private-key, ensure the account belongs to Debian's sudo group, and use --ask-become-pass only in an interactive terminal.

Docker Compose install or container check fails

Read the per-host task error, inspect sudo systemctl status docker and sudo docker compose -f /opt/law/compose.yaml logs. APT requires working Internet/DNS and Docker's signed repository.

Windows needs to be preserved

Stop before disk partitioning and use another SSD, a backup-based migration, or a VM pilot. This guide does not silently erase Windows.
